# Передача проекта

Состояние на 5 октября 2026 года. Разработка продолжена через корпоративные подключения GitHub, Supabase и Railway. Использовать только корпоративные аккаунты и ресурсы.

## Назначение и правила

Сервис должен работать для **Verona Home + WallPanels** через HighLevel, Telegram Bot, Supabase, корпоративный GitHub и Railway. HighLevel используется только для чтения. Режим испытаний (`TEST_MODE=true`) направляет уведомления только Дмитрию. Переход в рабочий режим требует отдельного разрешения владельца.

Нужно отслеживать **все клиентские каналы сообщений**: SMS, Email, WhatsApp, Instagram, Facebook, Live Chat/WebChat, GMB и новые типы входящих сообщений, которые вернёт HighLevel. Выгрузка без параметра `channel` получает сообщения кроме Email; отдельная выгрузка с `channel=Email` получает Email. Звонки не запускают таймер без реального входящего текстового сообщения. Ожидание закрывает только настоящий исходящий ответ сотрудника, а не сообщение из workflow, campaign, API, бота или другого автоматического источника. Пороговые уведомления: **60/90/120 минут** в рабочем режиме и **2/4/5 минут** в режиме испытаний.

## Сделано локально

- Проект опубликован в корпоративном репозитории `Wallpanels-com/sales-control`, ветка `main`. Добавлен GitHub Actions workflow для typecheck, tests и build. Владелец временно сделал репозиторий публичным для подключения Railway; секретов в репозитории нет.
- `.env.local` создан из разрешённого владельцем документа, права файла ограничены; он игнорируется Git. Секреты в этом файле не приводятся здесь.
- Реализованы чтение и раздельная выгрузка каналов HighLevel, нормализация канала, исключение звонков, хранение состояния ожидания и единая логика SLA. Неизвестный тип с текстом или вложением сохраняется как `Other:<тип>`.
- Для определения ответа сотрудника используется известный HighLevel `userId` и источник `app`, который наблюдался в реальной выгрузке Verona. Неизвестные источники не закрывают SLA.
- Добавлены маршрутизация по владельцу открытой Opportunity, затем Conversation, затем Contact; сопоставление сотрудников по точному имени; запасная отправка руководителю и администратору; Telegram `/start`, `/status`, `/test_alert`; `/health`; миграция БД; инструкции запуска. Схема обновлена отдельными таблицами `telegram_users`, `sla_incidents`, `assignment_mismatches` и `system_logs`.
- Реальные запросы **GET** к Verona HighLevel подтвердили доступ к локации, 17 пользователей, экспорт SMS и Email, а также наличие звонков в выгрузке без `channel`. Ручные исходящие SMS и Email имели `source=app`; workflow-сообщения также имели `userId`, поэтому одного `userId` недостаточно для распознавания ответа человека. WhatsApp, Instagram, Facebook и WebChat в доступном образце не встретились. Telegram Bot API ответил на проверку токена.
- TypeScript-проверка, 4 теста и сборка прошли после последних изменений.
- Обе миграции применены к корпоративному Supabase `wpvh-sales-control`. Созданы 11 таблиц, RLS включён, публичные права отозваны, предупреждение о публичной `SECURITY DEFINER`-функции устранено, внешние ключи проиндексированы.
- Локальный сервис успешно синхронизировал Verona, 17 HighLevel-пользователей и 3 точных sales-сопоставления. `/health` вернул `200` в `TEST_MODE=true`.
- Дмитрий зарегистрирован через Telegram `/start`; тестовое Telegram-уведомление успешно отправлено.
- Временный интеграционный тест подтвердил: inbound открывает SLA, workflow не закрывает SLA, ручной `app`-ответ закрывает SLA, calls игнорируются, новый текстовый канал сохраняется. Тестовые записи удалены.
- Корпоративный Railway-проект `wpvh-sales-control` подключён к `main`, успешно собран на Node 22 и работает с одной репликой. Публичный `/health` вернул `200`, `TEST_MODE=true`, Verona и пороги 2/4/5 минуты.
- Причина первой ошибки Railway: Railpack сначала устанавливал зависимости, а затем пользовательская команда повторно запускала `npm ci`; на втором этапе lock-файл был недоступен. Также Node 20 не соответствовал требованию Supabase SDK `>=22`. Команда сборки заменена на `npm run build`, runtime и CI переведены на Node 22.
- Подтверждён шаблон кнопки `Open Conversation` для Verona из предоставленной реальной ссылки. Тестовое Telegram-уведомление с кнопкой на эту conversation успешно отправлено Дмитрию.
- Контролируемый Railway-тест подтвердил полный цикл: тестовый inbound открыл SLA, после 2 минут Railway отправил ровно один Telegram alert, тестовый ручной `app`-ответ закрыл инцидент, а на 4-й и 5-й минутах новых alerts не появилось. Временные строки теста удалены.
- WallPanels добавлен как вторая компания с отдельным `locationId` и отдельной строкой company. Read-only API-проверка подтвердила Location, 36 Users, Conversations, Messages, Contacts и Opportunities. В реальной выгрузке встретились Email, Facebook, Instagram, SMS и WhatsApp; calls исключены. Источники `app` и `workflow` различаются, поэтому действующее human reply правило подходит без изменения.
- В Supabase синхронизированы 36 WallPanels users и 3 точных staff mappings. Реальная проверка маршрутизации WallPanels выбрала Opportunity Owner; выбранный владелец присутствует среди users этой локации. `locationId` Verona и WallPanels различаются.

## Не завершено и ограничения

- В Railway остался созданный владельцем дубликат проекта `miraculous-spontaneity` с неудачной старой сборкой. Рабочий сервис находится в проекте `wpvh-sales-control`; удалять дубликат без явного решения владельца не требуется.
- Команду Telegram `/status` нужно проверить вручную из зарегистрированного аккаунта Дмитрия.
- Для WebChat пока нет живого примера ни в одной из проверенных выгрузок; классификатор и единая SLA-логика его поддерживают.

## Следующие шаги для другого корпоративного Codex-аккаунта

1. В `TEST_MODE=true` проверить `/status` и провести один настоящий входящий тест из HighLevel, чтобы подтвердить весь внешний путь от HighLevel export до Telegram без синтетической записи.
2. При необходимости провести отдельный полный SLA-тест по Email, WhatsApp, Instagram и Facebook; эти типы уже подтверждены в живой WallPanels-выгрузке.
3. Провести один настоящий входящий тест WallPanels в `TEST_MODE=true` и проверить кнопку `Open Conversation` в интерфейсе HighLevel.
4. Решить, оставить ли репозиторий публичным, и удалить лишний Railway-проект `miraculous-spontaneity`, если он больше не нужен.
5. Переключить на рабочие 60/90/120 минут и `TEST_MODE=false` только после отдельного согласия владельца.
