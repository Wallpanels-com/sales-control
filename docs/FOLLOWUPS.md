# Напоминания о follow-up

## Расписание

1. Клиент написал → sales ответил вручную → 24 часа молчания клиента → напоминание №1.
2. Sales действительно отправил первый follow-up после напоминания → 48 часов молчания → напоминание №2.
3. Sales действительно отправил второй follow-up после напоминания → 96 часов молчания → напоминание №3.
4. После третьего отправленного follow-up цепочка завершена. Ответ клиента на любом этапе останавливает её; новый ответ sales на новое сообщение клиента начинает новую цепочку.

Часы непрерывные, не рабочие дни. Несколько частей одного ответа не считаются несколькими follow-up. Кнопка Copy лишь копирует текст; она не пишет в CRM и не меняет этапы. Если sales не отправил follow-up, следующее напоминание не возникает просто из-за прошедшего времени.

## Режимы

- `off`: модуль не отслеживает и не отправляет follow-up. Безопасное значение по умолчанию.
- `preview`: отслеживает новые события начиная с FOLLOWUP_CUTOVER_AT; автоматическая отправка отсутствует даже Dmitry. Разрешён отдельный однократный запуск демо/preview только для Dmitry.
- `production`: после отдельного подтверждения владельца — ответственный sales + зарегистрированные manager/admin, как у текущего SLA. При глобальном TEST_MODE=true отправка этого модуля блокируется.

Новые переменные: FOLLOWUP_GROQ_API_KEY, FOLLOWUP_MODE, FOLLOWUP_CUTOVER_AT. Значения ключей хранятся только в игнорируемом локальном env и корпоративных Railway Variables.

## Тестовый пример

`npm run followup:demo`: AI получает исключительно вымышленную переписку. Из настоящей CRM читаются только ID для проверки кнопки. В уведомлении явно написано, что переписка вымышленная, а CRM-кнопка служит проверке ссылки. Получатель — только существующая запись Dmitry с numeric chat ID. В followup_notifications сохраняется preview=true.

`npm run followup:preview`: использует настоящие сообщения клиента с Groq. Не запускать без прямого согласия на передачу клиентского текста внешнему AI. Читает текущую CRM переписку, проверяет отсутствие более позднего ответа, генерирует один подходящий пример. Не продвигает production-цепочки.

`npm run followup:preview -- mariarayme`: тот же однократный пример, только по лиду Mary. Текущий ответственный проверяется по CRM до отправки текста в AI. Получатель теста — только Dmitry.

## Защита

- Данные компаний разделены по company_id и проверенным locationId/contactId/conversationId.
- Перед генерацией проверяется свежая переписка HighLevel; перед боевой отправкой повторно проверяется состояние в Supabase и свежесть синхронизации.
- Ответственный определяется существующей функцией: Opportunity Owner → Conversation Assigned User → Contact Owner → manager/admin.
- AI может отменить неуместное напоминание или перенести его до явно согласованной даты. Неуверенный результат/API-сбой не создаёт уведомление; повторная проверка через 30 минут.
- AI явно получает отправителя-sales, получателя-клиента и роль автора каждого сообщения. Ответ пишется от sales клиенту; обращение к sales вместо клиента отклоняется кодом. AI не должен выдумывать доступность клиента или назначать встречу от его лица.
- Ключи, транспортные ошибки и клиентский текст не пишутся в журналы приложения.
- Отдельные таблицы followup_threads/followup_notifications имеют RLS и не доступны anon/authenticated.
- Уникальный dedupe_key защищает от повторов. Неопределённый результат Telegram не пересылается автоматически, чтобы избежать дублей; проверяется вручную.
- Состояния меняются с проверкой предыдущего event key/status, чтобы параллельный импорт не перезаписал факт отправленного напоминания.

## Включение на команду — только после подтверждения

1. Получить подтверждение текста/кнопок и прямое согласие на использование реальной клиентской переписки в Groq для этого модуля.
2. Проверить корпоративный Railway-доступ, применённую migration, health и тесты.
3. Выбрать новый UTC cutover; пометить старые preview-цепочки как suppressed, сохранив историю. Не удалять текущие SLA incidents.
4. Установить FOLLOWUP_CUTOVER_AT, FOLLOWUP_GROQ_API_KEY и FOLLOWUP_MODE=production в Railway. Убедиться в TEST_MODE=false.
5. Проверить адресатов: sales только свои conversations, руководители — общий контроль. Старые follow-up ожидания до cutover не должны массово отправляться.

Обычный SLA 60/90/120 минут не изменён.
